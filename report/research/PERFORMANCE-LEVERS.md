## 1. Fast 2-opt for TSP

### (a) Neighbour lists / candidate lists

Restrict 2-opt to each city's k nearest neighbours (by Euclidean distance) instead of scanning all n−1 other cities. For city X1 with tour successor X2, only consider candidate cities Y1 drawn from X1's precomputed neighbour list (sorted by distance), because an improving 2-opt move requires d(X1,Y1) < d(X1,X2) — if even the *nearest* untried neighbour is already farther than the edge you're trying to break, no candidate further down the list can improve it, so the inner scan can stop early (an implicit branch-and-bound pruning rule described in Bentley's paper).

- Typical k values used in practice: 5, 8, 10, 20 (project's own framing) — Bentley (1992) and subsequent codes (e.g. Concorde, LKH) commonly use k in the 5–20 range; empirical tests summarized by third-party writeups (tsp-basics) used k=24/48/99 and observed near-linear reduction in work: complexity per pass becomes **O(n·k)** instead of **O(n²)**, with observed wall-clock reduction roughly proportional to k/n in their instrumented example.
- Quality impact: candidate-list-restricted 2-opt very rarely misses the *true* best 2-opt move for spatial TSP instances, because in practice almost all improving 2-opt moves involve geometrically nearby cities; Johnson & McGeoch's extensive empirical study of local optimization for TSP is the standard reference establishing this for 2-opt, Or-opt, and Lin–Kernighan style neighbourhoods, and documents that neighbour lists of moderate size (~10–20) recover solution quality statistically indistinguishable from unrestricted search while being drastically faster.

Pseudocode (candidate list construction, k nearest by brute force or k-d tree):
```
for each city i:
    neighbors[i] = the k cities j != i with smallest dist(i, j),
                   sorted ascending by distance
```
Build once per problem instance (coordinates are fixed for the whole GA run), reused by every island/generation — this amortizes the O(n² ) or O(n log n) (k-d tree) construction cost across the entire optimisation.

### (b) Don't-look bits (Bentley / standard technique)

Maintain a boolean array `dontLook[city]`, initially all `false` (i.e., all cities "active"). The 2-opt local search processes a queue/scan of active cities:

```
queue = all cities (e.g. in tour order), dontLook[*] = false
while queue not empty:
    x1 = pop from queue
    if dontLook[x1]: continue
    improved = false
    for x2 in {succ(x1), pred(x1)}:           # both tour neighbours
        for y1 in neighbors[x1]:                # candidate list, ascending distance
            if dist(x1, y1) >= dist(x1, x2): break   # pruning: sorted list, no farther candidate can help
            y2 = the tour neighbour of y1 on the same side as x2 relative to x1
            gain = dist(x1,x2) + dist(y1,y2) - dist(x1,y1) - dist(x2,y2)
            if gain > 0:
                perform 2-opt swap (reverse the segment between x2 and y1)
                dontLook[x1] = dontLook[x2] = dontLook[y1] = dontLook[y2] = false
                push x1, x2, y1, y2 onto queue (they are re-activated)
                improved = true
                break out of both inner loops
        if improved: break
    if not improved:
        dontLook[x1] = true     # no improving move found from x1; skip it until reactivated
```

Key mechanics, confirmed against the standard description (Bentley 1992; summarized consistently by independent TSP-implementation writeups):
- The bit is **set to true (skip)** only when a full search from that city (both tour-neighbour directions, full candidate list) finds no improving move.
- The bit is **reset to false (re-examine)** for exactly the four cities that are endpoints of the two edges changed by an accepted move (both endpoints of the removed edges / both endpoints of the added edges) — i.e., `x1, x2, y1, y2` above. These are exactly the cities whose local edge structure changed, so only they can newly have an improving move available.
- After the first full pass, most cities' bits stay `true` for the rest of the local search; work concentrates on the small, shrinking set of cities near recent changes.

### (c) Combination — achieved complexity

Neighbour lists bound the candidate set examined per city to O(k); don't-look bits bound the number of cities actually re-examined after the first pass to those touched by recent moves. The combination is reported (Bentley 1992; reinforced by Johnson & McGeoch 1997, and standard in production codes such as Concorde and LKH) to behave close to **linear in n per full local-optimum computation** on geometric instances in practice, versus **O(n²)** (or worse, since each pass may need to be repeated) for naive first-improvement 2-opt scanning all pairs every pass. This is an empirically observed practical complexity on geometric/random Euclidean instances, not a worst-case asymptotic guarantee — pathological inputs can still force more work.

For this project's n = 500–800, naive 2-opt is O(n²) ≈ 250,000–640,000 distance evaluations *per call*, invoked with probability 0.2 per child; neighbour-list + don't-look-bits 2-opt is expected to cut this by roughly the ratio n/k (a factor of ~25–100 for k=8–20), consistent with the qualitative O(n·k) vs O(n²) scaling from §1a — the exact multiplier for this codebase is **unverified** without profiling.

### (d) Or-opt / 2h-opt / Or-3opt — worth adding?

Or-opt relocates a short chain of 1–3 consecutive cities to a different position in the tour (a restricted 3-opt move that does not require full segment reversal, so its cost per move is O(1) with a linked-list tour representation, or O(n) worst case with an array representation for the shift). It is a standard complement to 2-opt because 2-opt alone cannot fix certain "city stuck in the wrong place" patterns that Or-opt fixes directly, and vice versa — this combination is discussed by Glover and summarized in Johnson & McGeoch's case study as one of the standard "2-opt + Or-opt" local search neighbourhoods used by high-quality TSP heuristics before escalating to full Lin–Kernighan. Given this project already budgets 2-opt at p=0.2 per child, adding Or-opt is a moderate-effort addition with plausible (but **unverified** for this codebase) further quality/speed benefit; it should be evaluated only after neighbour-list+DLB 2-opt is in place, since Or-opt is typically layered on top of, not instead of, that infrastructure.

### (e) Segment reversal cost and the standard mitigation

For an array-based tour representation, executing a 2-opt move requires reversing the sub-array between the two cut points — O(segment length), worst case O(n). The standard, essentially free optimisation is to **reverse whichever of the two segments (inside vs. outside the cut) is shorter**, using tour-position wraparound; since the two segments partition the n cities, the shorter one is at most n/2, giving an average-case reversal cost of roughly n/4 instead of up to n. This is explicitly documented in Helsgaun's LKH report as one of the fundamental implementation techniques.

For asymptotically sub-linear reversal, two structures are used in serious codes:
- **Doubly linked list of cities** — makes traversal and single-edge changes O(1) but loses O(1) "is city A before city B in the tour" ordering queries, which 2-opt/Or-opt need to decide which side to reverse and to bound segment length.
- **Two-level list** (segment list of √n-sized blocks, each with a reversal flag) — the data structure used by LKH-style codes, giving O(√n) per reversal and O(1) amortised neighbour/sequence queries. This is a materially larger engineering effort (a full tour-representation rewrite) than the shorter-side trick.

At this project's n = 500–800, the shorter-side array trick (an O(n) worst case, ~n/4 average) is very likely sufficient — the crossover point where two-level lists start to dominate is typically cited in the LKH literature as being relevant for much larger instances (n in the thousands to millions), where O(n) reversals per move, repeated over many moves, become the dominant cost. For n≤800 the *reversal* cost is dwarfed by the O(n²) (or O(n·k) with candidate lists) move-search cost, so the two-level list is **L effort for likely small return at this problem size** — recommended only if profiling after §1a/§1b shows reversal time as a measured hotspot.

## 2. Distance matrix and memory

- A full n×n `double` distance matrix is 2 MB at n=500 and 5.1 MB at n=800 (given). This is comparable to or exceeds typical desktop-class L2 (256 KB–2 MB per core on this generation of Intel parts) and consumes a large fraction of the 6 MB shared L3, especially when multiple islands each hold/scan their own copy or when several islands share the L3 concurrently under OpenMP.
- Full O(n²) memory for a dense distance matrix is explicitly identified in the TSP literature as the practical scaling limit of matrix-based approaches; codes intended to scale past tens of thousands of cities avoid a dense matrix altogether and either recompute distances on demand or store only candidate-list (k-nearest-neighbour) distances (general finding, not this project's own measurement — cite general TSP scaling discussion, **magnitude unverified for n≤800 specifically**, since at these small n the matrix comfortably fits main memory; the concern here is cache residency, not total memory).
- **On-the-fly recomputation vs. matrix**: at n = 500–800 a full matrix (2–5 MB) does not fit L2 but does fit L3 (6 MB) with room to spare for one island; with multiple islands contending for the shared L3 under OpenMP, effective L3 residency per island shrinks, increasing the fraction of matrix lookups that miss to DRAM. Recomputing `sqrt((x1-x2)^2+(y1-y2)^2)` on the fly avoids memory traffic entirely at the cost of a `sqrt` (a few cycles on modern hardware, often software-pipelined by `-O3 -march=native`) — whether this crosses over to being faster than a matrix lookup depends on the achieved cache hit rate, which is workload- and hardware-specific and **unverified** without direct profiling on this machine. The standard trade-off argument (recompute vs. cache) is well established in numerical/HPC practice generally, but no source found gives a TSP-GA-specific number for this exact n range and cache size, so treat as a hypothesis to validate, not a proven win.
- **k-nearest-neighbour-only caching**: once candidate lists (§1a) are adopted for 2-opt, a natural companion optimisation is to cache only the k·n neighbour distances actually used by the restricted local search, rather than the full n² matrix. For k=10–20 and n=800, this is 8,000–16,000 doubles (64–128 KB) instead of 5.1 MB — comfortably L2-resident. Note this only covers 2-opt's own distance lookups; **fitness evaluation** (full tour length) and **OX crossover** do not restrict to neighbours and still need all n pairwise distances along the tour edges actually present — which can be satisfied by on-the-fly recomputation instead of a full matrix, since only n lookups (the tour's own edges) are needed per fitness evaluation, not n².
- **float vs. double**: TSPLIB's EUC_2D edge-weight type is explicitly defined as `nint(sqrt(xd*xd+yd*yd))` — an **integer-rounded** distance (confirmed by the TSPLIB95 specification). This means the "true" precision of the distance values used by canonical TSP benchmarks is integer, not double-precision float. A `float` (or even `int`/`int32_t`) distance matrix loses no meaningful precision relative to that convention and halves (or quarters, for `int32_t`) the matrix footprint versus `double`, directly reducing cache pressure at both n=500 and n=800. The tour-length **accumulator** (sum of n up to ~800 edge distances) should still use a type wide enough to avoid rounding drift across many additions (double or a 64-bit integer accumulator, depending on whether the project uses integer or real-valued distances) — narrowing only the per-edge storage, not the running sum, is the safe version of this change.

## 3. Cheaper diversity metrics

The current diversity metric builds an `std::unordered_set<long long>` of the best tour's n edges per epoch and, implicitly, compares against other individuals' edges — O(pop·n) work with hash insert/lookup overhead per edge, which the project's own measurement identifies as the dominant per-epoch serial cost (11.04 s → 3.63 s when epoch length rises from 1 to 250, i.e., ~7.4 s of avoidable serial bookkeeping at epoch=1, attributed to the diversity metric and publish copies).

Cheaper, same-signal alternatives, cheapest first:

1. **Bitset edge-set + popcount intersection (recommended default).** Encode each undirected edge (a,b) with a<b as a single integer key, e.g. `key = a*n + b` for n≤~65536 (fits in a 32-bit or 64-bit int, no hashing needed). For a tour of n cities there are exactly n edges out of n(n−1)/2 possible; represent an individual's edge set as a `std::bitset<N*(N-1)/2>` or (more practically) as a **hash-free flat array** `std::vector<bool>` / raw bitset indexed by the same key, one array per compared individual, or maintain **one shared "reference" bitset for the current best tour** and, for each other individual, walk its n edges and test membership in that bitset with O(1) array/bit lookups (no hashing, no allocation) — this is a direct drop-in replacement for the `unordered_set` membership test, with `pop*n` bit tests (cheap, branch-predictable) instead of `pop*n` hash operations (cache-unfriendly, allocation-prone).
   - Cheapest correct way to compute `|A ∩ B|` for two tours' edge sets: represent both as bitsets over the same n(n−1)/2-length edge-index space and compute `popcount(A & B)` using word-at-a-time AND + hardware `POPCNT` (compiler intrinsic `__builtin_popcountll` or `std::popcount` in C++20) — this turns an O(n) hash-based loop into O(n²/64) word operations only if using the *full* dense bitset (rarely worth it at n=800, since n(n-1)/2 ≈ 320,000 bits ≈ 40 KB per individual — plausible but memory-heavy across a whole population); the more memory-frugal and equally correct approach for this project's specific need (edges of the best tour vs. edges of each other individual, not all-pairs) is: build one bitset/hash-free membership array sized to the *actual* n edges of the reference tour (not all possible pairs), keyed by e.g. a sorted-pair index into a compact array via a perfect map from the n tour edges to indices 0..n−1, and then for every other individual just test each of its n edges against that array — O(n) per individual with O(1), allocation-free lookups, i.e. the same asymptotic complexity as today (O(pop·n)) but with a dramatically smaller constant factor (array indexing vs. hash-table insert+probe+dynamic allocation).
2. **Sampling a subset of individuals.** Compute the same edge-overlap statistic against only a random sample of, e.g., √pop or a fixed constant (16–32) individuals rather than the whole population, trading exactness for an O(sample·n) cost independent of population size. This changes the exact numeric value of the diversity statistic (estimation noise), so it has a reproducibility implication if the statistic feeds back into any adaptive control (e.g., mutation-rate adaptation) — flagged as Medium risk in the summary table only when combined with such feedback; if diversity is purely diagnostic/logging, risk is Low.
3. **Fitness-variance / fitness-entropy proxy.** Replace the structural (edge-overlap) diversity signal with a purely numeric one — variance or entropy of the population's fitness (tour-length) values, an O(pop) computation with no per-edge work at all. This is much cheaper but measures a different thing (fitness spread, not genotypic/structural spread); two structurally very different tours can have similar length. Acceptable only if the project's use of "diversity" tolerates this substitution — a semantic change, not just a performance one, so it should be a deliberate design decision rather than treated as a drop-in.
4. **MinHash / sketch-based set similarity.** MinHash approximates Jaccard similarity `|A∩B|/|A∪B|` between two edge sets using a small fixed number of hash "fingerprints" per set instead of the full edge list, giving an approximate answer in O(sketch size) instead of O(n) per comparison. For this project's per-tour edge-set sizes (n ≈ 500–800, i.e. already small), a sketch would need to be considerably smaller than n to pay off, and MinHash introduces estimation error plus extra hashing overhead per element to build the sketch in the first place — it is the standard tool for *very large* sets or *many pairwise* comparisons (its usual use case), and is likely **over-engineered** for this project's scale; recommended only if diversity needs to be computed pairwise across the *whole* population (O(pop²) comparisons) rather than each-individual-vs-best (O(pop) comparisons), which is not what the project currently does.

**Concrete recommendation:** replace the `unordered_set<long long>` with a flat boolean array (or `std::bitset`) sized to n·(something small, e.g. a direct city-pair-to-slot map built once when the reference/best tour is published) and test edges in O(1) array lookups; skip MinHash as unnecessary at this n and comparison pattern; treat fitness-variance as a fast fallback/secondary signal, not a replacement, unless a semantic change is acceptable.

## 4. Selection and sorting

The population is `std::sort`-ed in full, twice per generation, though only the top `elites` and the bottom-K (migration) positions are actually needed in order, and tournament selection needs no global ordering at all (it only compares k=4 randomly drawn individuals against each other).

- **`std::nth_element`** partitions a range so the element at a given position is the one that would be there in a fully sorted range, with everything before it ≤ and everything after it ≥ that value — average-case **O(n)** (linear), versus `std::sort`'s **O(n log n)** — this is the right primitive to isolate a migration cutoff (worst-K boundary) or an elite-count boundary without paying for full order (cppreference / C++ standard complexity guarantees).
- **`std::partial_sort`** fully sorts only the first k elements of a range (the rest are left in an unspecified but not-less-than order) in **O(n log k)** — the right primitive when you need the top-`elites` individuals *in order* (e.g., because migration always sends the single best, or elites are copied in rank order), which `nth_element` alone does not guarantee.
- Recommended pattern for this project: replace each full population sort with:
  1. `std::nth_element(pop.begin(), pop.begin()+elites, pop.end(), byFitness)` to place the elite/non-elite boundary, optionally followed by `std::partial_sort(pop.begin(), pop.begin()+elites, ...)` only if elites must themselves be rank-ordered (e.g., "top individual" vs. "top-K in some priority").
  2. A second, independent `nth_element` (or a single combined pass, since elite-boundary and migration-worst-boundary are just two different order statistics on the same array) for the migration-worst-K boundary, rather than relying on a full ascending sort to read off both ends.
  3. Tournament selection remains untouched — it already only needs pairwise fitness comparisons among k=4 randomly indexed individuals, no ordering of the whole population, consistent with standard GA practice where tournament selection cost is O(k) per selection event and is not tied to whether the population is sorted.
- This is standard, well-documented C++ standard-library practice (not a TSP- or GA-specific finding) — the complexity guarantees for `sort` (O(n log n)), `partial_sort` (O(n log k)), and `nth_element` (average O(n)) are part of the C++ standard and consistently documented on cppreference; the GA-specific point — that elitism and migration only require order-statistics, not full ranking — is standard practice described in general elitism/GA implementation guides (Baeldung's elitism articles), though those sources describe the *algorithmic* need for a top-k cut, not the specific STL primitive to use, so the STL-mapping recommendation here is an engineering inference from the standard's guarantees, not a direct claim from a GA paper.

## 5. Random number generation

The code constructs a fresh `std::uniform_int_distribution`/`std::uniform_real_distribution` object on every call, drawing from a shared `std::mt19937_64` engine.

- **Cost of the current pattern:** `std::uniform_int_distribution` in most standard library implementations uses rejection sampling to avoid modulo bias, and constructing the distribution object per call (rather than once, reused) adds object-construction/parameter-computation overhead on every single random draw, on top of `mt19937_64`'s own per-call cost. Independent third-party benchmarks (Sam Thompson's C++ RNG shootout; the PCG-random project's own bounded-random writeup) consistently show `mt19937`/`mt19937_64` as markedly slower than modern small-state generators — one benchmark cited a roughly 5x throughput gap between the slowest engine tested and the fastest (`xoshiro256+`), with `mt19937` among the slow group, and separately, PCG's own documentation states PCG64 is roughly 2x faster than `mt19937_64` for 64-bit output. `mt19937`'s ~2500-byte (20,032-bit) internal state versus xoshiro256's 32-byte or PCG's 16-byte state also matters for cache footprint when many islands each hold their own engine.
- **Faster alternatives:**
  - **xoshiro256++ / xoshiro256\*\*** — small (256-bit) state, very fast, good statistical quality; xoshiro256++ is specifically recommended over xoshiro256\*\* when a 64-bit generator with the best available statistical profile is wanted (per the PRNG-shootout-style comparisons found). Public-domain reference implementations are available from the generators' original authors (Blackman & Vigna, prng.di.unimi.it).
  - **PCG family** — smaller state (128-bit for PCG64), documented ~2x throughput advantage over `mt19937_64`, plus a well-documented fast bounded-random technique (see below). Reference: PCG-random project (pcg-random.org), O'Neill's PCG paper/documentation.
  - **splitmix64** — extremely simple, fast, commonly used to *seed* the larger-state generators above (not usually the main generator itself, but relevant if per-island seeding is a cost).
- **Lemire's fast bounded integer generation** (Lemire, "Fast Random Integer Generation in an Interval," ACM TOMACS 29(1), 2019, DOI: 10.1145/3230636, also arXiv:1805.10941): replaces the classic modulo-based or full rejection-sampling approach to generating a uniform integer in [0, s) with a multiply-high-word technique that avoids integer division/modulo in the common case (division is only needed rarely, to compute a threshold, and the fast path is a 64-bit multiply and bit shift). This is a drop-in replacement for exactly the pattern this project uses (`uniform_int_distribution` for index draws in tournament selection, mutation point selection, crossover points, etc.) and is reported to substantially speed up unbiased ranged-random generation and shuffling on x64 hardware; Lemire also published a batched/vectorized follow-up ("Faster random integer generation with batching," 2024) for further gains when many bounded draws are needed back-to-back, as tournament selection (k=4 draws per selection event) would.
- **Recommended concrete implementation:** keep (or replace) the underlying bit-source with xoshiro256++ or PCG64, and replace every `std::uniform_int_distribution<>(lo,hi)(rng)` call site with a Lemire-bounded-random free function taking `(rng, range)` and returning an index directly, with no per-call distribution object construction. For `uniform_real_distribution`, the cheap analogous techniques exist (dividing a fixed-width random integer by its max value, or using the RNG's native float-generation trick as documented alongside xoshiro/PCG) but were not the focus of Lemire's paper.
- **Reproducibility implication (High risk — must be called out explicitly):** `mt19937_64` plus `std::uniform_int_distribution`'s rejection-sampling scheme, for a fixed seed, produces a bit-for-bit deterministic sequence of accept/reject decisions and outputs that is part of the C++ standard's specified behavior for that engine (though the distribution's exact algorithm is implementation-defined across standard libraries, so it is not even guaranteed portable across compilers today). Switching either the underlying engine (to xoshiro/PCG) or the bounded-sampling algorithm (to Lemire's technique) changes the exact sequence of pseudo-random decisions for the *same seed*, so any existing "golden" results, regression baselines, or reported experimental numbers tied to specific seeds will no longer reproduce bit-for-bit after this change — only the statistical/aggregate behaviour (mean tour length, convergence trends) should be expected to match. This must be treated as a breaking change to any seeded reproducibility contract, not a transparent internal optimisation, and ideally ships behind a flag or a version bump so old seeded results are understood to be pre-change.

## 6. OpenMP and SMT

- **OMP_PROC_BIND / OMP_PLACES on a 4-core SMT machine.** Standard OpenMP affinity guidance (HPC Wiki "Binding/Pinning"; general OpenMP affinity references) recommends `OMP_PLACES=cores` as the typical default binding granularity (one OpenMP "place" per physical core, not per SMT thread), with `OMP_PROC_BIND=close` favoring cache-sharing between nearby threads (appropriate when threads share data, e.g. islands reading a common distance matrix) versus `OMP_PROC_BIND=spread` favoring maximum aggregate memory bandwidth (appropriate when threads are largely independent and memory-bandwidth-bound). For this project's 4-core/8-SMT-thread part, `OMP_PLACES=cores` with 4 OpenMP threads restricts execution to the 4 physical cores (i.e., effectively opts *out* of SMT for the compute threads), which is the standard recommendation for compute-bound, non-memory-bandwidth-saturated per-core work; using `OMP_PLACES=threads` intentionally spans SMT siblings, which is the standard choice only when the workload is memory-*latency*-bound and can benefit from a second hardware context filling stalls. One general HPC example (matrix-multiplication style workload, not TSP-GA-specific) reported explicit affinity settings reducing runtime *variance* (6.23–8.94 s down to a tight 5.44–5.49 s band) more than they reduced the mean — i.e., affinity primarily reduces jitter and worst-case scheduling noise, and any absolute-speedup claim for *this* project's workload is **unverified** without direct measurement.
- **Does SMT typically help or hurt memory-bound irregular workloads like this?** The project's own measured strong scaling — 1.96x at 2 threads, 3.30x at 4 threads (i.e., full physical-core count), but only 3.93x at 8 SMT threads — shows a sharply diminishing return exactly at the physical-core boundary (going from 4 real cores to 4 additional SMT siblings adds only ~0.63x more speedup, versus ~1.34x added by the previous doubling from 2 to 4 real cores). This pattern — SMT siblings contending for the same core's execution units, cache ports, and memory bandwidth, yielding much smaller marginal gains than additional physical cores — is the textbook signature of a workload that is not purely compute-latency-bound-with-idle-cycles-to-fill (the case where SMT helps most), consistent with (though not proven by a specific cited benchmark for this exact algorithm) general HPC guidance that SMT gives the largest wins for workloads with high per-thread stall time and low per-core resource contention, and smaller or negative wins for workloads (like this GA's O(n²) 2-opt inner loops and the shared distance-matrix reads) that already keep the core's functional units and cache ports busy. Given this project's own Amdahl analysis (serial fraction 0.155) already explains much of the shortfall from ideal scaling independent of SMT effects, disentangling "SMT hurts" from "Amdahl's serial fraction caps everything beyond ~4x anyway" would require a dedicated experiment (e.g., comparing 4 threads pinned to 4 distinct cores vs. 4 threads allowed to share SMT-sibling pairs) that is **unverified** here.
- **OMP_WAIT_POLICY active vs. passive when oversubscribed.** General OpenMP runtime guidance: `active` (the default in most runtimes) keeps idle threads spin-waiting for new work, minimizing wake-up latency but burning CPU cycles and contending for shared resources (cache bandwidth, power/thermal budget) even while "idle" — appropriate when thread count ≤ hardware parallelism. `passive` puts idle threads to sleep (yielding/blocking), trading wake-up latency for not stealing cycles from other runnable work — the standard recommendation specifically for the **oversubscribed** case (more OpenMP threads, or more total application threads, than hardware contexts), which is directly relevant to this project's own observed p=6-on-8-islands anomaly if that configuration also oversubscribes the 4 physical cores (p=6 > 4 cores) — switching to `passive` in that specific oversubscribed regime is standard guidance to reduce spin-wait contention, though whether it fixes *this project's specific* p=6 slowdown (which the project itself attributes to load imbalance, not spin-wait contention) is a separate question and **unverified**.
- **Distributing I islands over T threads when T does not divide I.** The project's own observation — p=6 with 8 islands being *slower* than p=4 — is explained by `ceil(8/6) = 2`, meaning at least one thread must process 2 island-units while others process only 1, so the parallel region's wall-clock is bounded below by (2 island-units' worth of work), i.e. effectively the same lower bound as running only 4 threads with 2 islands each — extra threads (5th and 6th) are provisioned but do not shorten the critical path, while still paying full thread-management/barrier overhead for 6 threads instead of 4. This is the canonical OpenMP static-scheduling load-imbalance result: when work items don't divide evenly across threads under `schedule(static)` (the implicit default for a manually chunked parallel-for over islands), the maximum per-thread chunk size — not the average — determines wall-clock time. **Standard mitigations**, confirmed by general OpenMP scheduling literature (e.g. the comparative studies of OpenMP scheduling-algorithm selection found in current literature, and the well-established rationale behind `dynamic`/`guided` scheduling in the OpenMP specification itself):
  1. **Choose I as an exact multiple of T** (or T as a divisor of I) so every thread gets exactly I/T island-units — eliminates the imbalance structurally, zero runtime cost, and is the simplest fix directly applicable here (e.g., use 8 islands with p∈{1,2,4,8}, or use 6 islands with p=6, rather than mixing 8 islands with p=6).
  2. **`schedule(dynamic)` (or `schedule(dynamic, 1)`) over the islands-per-generation loop** instead of implicit static chunking — lets idle threads pull the next unassigned island as soon as they finish their current one, so the uneven-division penalty becomes a much smaller tail effect (only the last few islands can straggle) rather than a fixed doubling on the overloaded thread(s); this is more general (works for any I, T combination) at the cost of small per-chunk scheduling overhead and loss of the cache-locality benefits of static scheduling (each thread may no longer consistently own the same island's data across generations). `schedule(guided)` is a middle ground (large chunks early, shrinking chunks later) also documented as a load-imbalance mitigation in the OpenMP scheduling literature.
  Recommendation for this project specifically: prefer **choosing I as a multiple of T** as the primary fix (free, deterministic, preserves per-island data locality across generations, which matters since each island's population/state is presumably thread-local across the whole run) — reserve `schedule(dynamic)` for scenarios where T must vary at runtime and I cannot always be chosen as a multiple of it.

## Recommended implementation order

1. **Fix I/T mismatch (§6).** Change the island count or thread count so I is a multiple of T (e.g., use I=8 with T∈{1,2,4,8}, avoid T=6). *Confirming measurement:* re-run the strong-scaling sweep (1,2,4,8 threads, 8 islands) and specifically re-test p=6 with an island count chosen as a multiple of 6 (e.g., I=6 or I=12) — the previously observed p=6 slowdown relative to p=4 should disappear or invert.
2. **Cheapen the per-epoch diversity metric (§3).** Replace `unordered_set<long long>` edge-set construction with a flat array/bitset membership test against the published best tour's edges. *Confirming measurement:* re-run the epoch-length sweep (1 → 250) single-threaded; the 11.04 s baseline at epoch=1 should drop substantially while the epoch=250 baseline (3.63 s) stays roughly flat (since at epoch=250 the metric is computed rarely already) — the *gap* between epoch=1 and epoch=250 should shrink markedly, isolating how much of the original 7.4 s gap was the diversity metric specifically versus the publish-copies bookkeeping.
3. **Replace full `std::sort` (x2) with `nth_element`/`partial_sort` for elites and migration cutoff (§4).** *Confirming measurement:* per-generation wall-clock at a fixed population size (e.g. 240) with local search *disabled* (isolating sort cost from 2-opt cost) should drop measurably, and the drop should scale with population size (O(n log n) → O(n) difference grows with n).
4. **Add neighbour lists + don't-look bits to 2-opt (§1a, §1b).** *Confirming measurement:* with local-search probability fixed at 0.2, measure wall-clock with local search enabled vs. disabled before and after this change — the *marginal cost* of enabling local search should drop sharply (ideally by roughly the n/k factor discussed in §1c), while final tour quality (best-of-run tour length) should remain statistically indistinguishable from the naive-2-opt baseline (per Johnson & McGeoch's finding that candidate-list-restricted 2-opt does not materially harm solution quality).
5. **Narrow the distance matrix to float (or cache only k-NN distances) (§2).** *Confirming measurement:* re-run at n=800 (worst case, 5.1 MB→2.55 MB) and look for reduced L3-miss-driven slowdown, e.g. via wall-clock at high thread count (where L3 contention across islands is worst) relative to single-threaded — if the float change specifically targets cache contention, the *relative* multi-thread speedup (not just absolute time) should improve slightly; also confirm final tour lengths are unchanged or change only in the last decimal of precision, consistent with TSPLIB's already-integer-rounded distance convention.
6. **Swap the RNG engine and adopt Lemire-bounded sampling (§5) — last, and only if profiling still shows RNG as a hotspot after steps 1–5.** *Confirming measurement:* microbenchmark calls/sec for index generation before/after: swap in the new engine behind a compile-time flag, keep the old path available, and confirm identical *statistical* behavior (mean/variance of final tour lengths across many seeds) even though exact seeded sequences will differ — document the reproducibility break explicitly in the project's own change log before merging.
7. **Tune OMP_PROC_BIND/OMP_PLACES/OMP_WAIT_POLICY (§6) — evaluate last since effects are expected to be small/variance-reducing rather than mean-shifting.** *Confirming measurement:* repeated runs (n≥10) at each candidate affinity/wait-policy setting, comparing both mean wall-clock and its variance; look specifically for variance reduction (per the general HPC affinity example found in research) rather than assuming a large mean speedup.
